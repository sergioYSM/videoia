# Architecture: videoia

Built from `replica/recon.md` and `replica/features.csv`. Same features as the
original where they are allowed; none of its code, private endpoints or models.
Videos are generated by third-party model APIs with **our own keys**.

## 1. Stack

| layer | choice | why |
| --- | --- | --- |
| web app | Next.js 15 (App Router) + TypeScript | same as Clipsong and Ownframe: one codebase to maintain, server routes for webhooks |
| styling | Tailwind, tokens from `/replica-design` | tokens generated, never hand-picked colours |
| database | Postgres on Supabase | ledger needs real transactions and row locks; RLS for per-user access |
| data access | `@supabase/supabase-js` + SQL functions | the money paths (`start_generation`, `fail_generation`, `grant_credits`) live in the database, one transaction each |
| auth | Supabase Auth (email magic link + Google) | already proven in Clipsong |
| payments | Stripe Checkout (subscriptions + one-off credit packs) + webhooks | idempotent webhook pattern reused from Clipsong |
| video models | **fal.ai** queue API, behind a `VideoProvider` interface | many models (Kling, Minimax/Hailuo, Wan, Luma…) behind one key and one queue + webhook API; a `mock` provider for dev and tests |
| moderation | provider's safety checker + our own prompt blocklist + image checks | the original's main abuse risk |
| files | Supabase Storage, private buckets, signed URLs | input images and copied outputs; provider URLs expire, so we copy |
| jobs | provider webhook (primary) + Vercel Cron every 2 min (reconcile) | webhooks get lost; the cron finishes or fails anything stuck |
| email | Resend | receipts, "your video is ready" (opt-in) |
| hosting | Vercel | same as the other apps |

One database, one app, no workers to run: the provider does the heavy compute.

## 2. Schema

In `supabase/migrations/0001_init.sql`. 7 tables:

| table | what | owner | notes |
| --- | --- | --- | --- |
| `profiles` | display name, plan | `id = auth.users.id` | created by trigger on sign-up |
| `credit_balances` | current balance | `user_id` pk | `check (balance >= 0)`; read-only to users |
| `credit_ledger` | every credit movement | `user_id` | append-only; `idempotency_key unique`; `balance_after` for audit |
| `uploads` | input images | `user_id` | ≤ 20 MB, mime checked; storage path per user |
| `generations` | one job | `user_id` | status `queued → running → succeeded / failed / cancelled`; `unique(provider, provider_job_id)`; partial index on open jobs for the reconcile cron |
| `subscriptions` | Stripe state | `user_id` | written only by the webhook |
| `stripe_events` | processed event ids | - | webhook dedupe |

Access: **row level security** on every table. Users can read their own rows,
insert their own uploads, flip `favourite` on their own generations and delete
finished ones. Every write that touches credits goes through a
`security definer` function; table-level `insert/update/delete` on the money
tables is revoked from `authenticated` and `anon`.

The money functions:

- `start_generation(...)`: checks the upload belongs to the caller, inserts
  the generation and charges `cost` in **one transaction** with the balance row
  locked (`for update`). Not enough credits → `insufficient_credits`, nothing
  created.
- `fail_generation(id, error)`: server only. Marks failed and refunds with key
  `refund:<id>`. A second failure report, or a failure after success, does
  nothing.
- `grant_credits(user, amount, reason, key)`: server only (Stripe webhook,
  monthly plan grant).

Proven by `npm run test:db` (real Postgres, 6 tests): grant idempotency, charge
atomicity, **20 concurrent charges against a balance of 70 → exactly 7
succeed**, refund once, no refund after success, RLS denials.

Cost is computed **on the server** from `lib/models.ts` (model × duration ×
resolution), never trusted from the client.

## 3. API

### Generation flow (F01 text→video, F02 image→video)

| method path | what | who | input | output |
| --- | --- | --- | --- | --- |
| `GET /api/models` | models, presets, prices | anyone | - | list with credit cost per duration |
| `POST /api/uploads` | signed upload URL for an input image | user | mime, bytes | upload id + URL |
| `POST /api/generations` | moderate prompt/image, compute cost, `start_generation`, submit to provider | user | prompt, model, preset, aspect, duration, upload id? | generation (status queued) |
| `GET /api/generations?cursor` | gallery page | user | filters | list |
| `GET /api/generations/:id` | one job (poll every 3 s while open; Supabase Realtime later) | owner | - | status, progress, signed video URL |
| `POST /api/generations/:id/cancel` | cancel at provider if still queued, refund | owner | - | status |
| `POST /api/generations/:id/regenerate` | same settings, new seed, new charge | owner | - | new generation |
| `PATCH /api/generations/:id` | favourite | owner | `{favourite}` | ok |
| `DELETE /api/generations/:id` | delete row + files | owner | - | ok |

### Credits and billing (F03)

| method path | what | who |
| --- | --- | --- |
| `GET /api/credits` | balance + last 50 ledger rows | user |
| `POST /api/checkout` | Stripe Checkout session (plan or pack) | user |
| `POST /api/portal` | Stripe customer portal (cancel in two clicks) | user |

### Webhooks in

| path | from | does |
| --- | --- | --- |
| `POST /api/webhooks/fal` | fal.ai | verify signature, find job by `provider_job_id`; on success copy video + thumbnail to Storage, mark succeeded; on error `fail_generation` |
| `POST /api/webhooks/stripe` | Stripe | verify, dedupe in `stripe_events`; `checkout.session.completed` → `grant_credits` key `stripe:<event>`; `invoice.paid` → monthly grant key `plan:<sub>:<period>` |

### Background jobs

| job | schedule | does |
| --- | --- | --- |
| reconcile | every 2 min | for jobs queued/running > 2 min: ask the provider for status; finish or fail. Running > 15 min → fail + refund |
| cleanup | daily | delete orphan uploads > 24 h, generations of deleted accounts |

### Providers

`lib/providers/{types,fal,mock}.ts`: `submit(input) → jobId`, `status(jobId)`,
`cancel(jobId)`. `mock` returns a stock clip after a few seconds (and fails on
prompts containing `fail`) so the whole app runs with no key and in e2e tests.

## 4. The parts that bite

- **Idempotency**: provider and Stripe webhooks arrive twice or out of order.
  Every credit movement has a unique key; job updates are guarded by status.
  Tested.
- **Race conditions**: two tabs pressing Generate at once. Balance row lock +
  `check (balance >= 0)`. Tested with 20 concurrent charges.
- **Lost webhooks / provider timeouts**: reconcile cron; hard timeout with
  automatic refund. The user never pays for a video they did not get.
- **Provider URLs expire**: copy outputs into our Storage before marking
  succeeded.
- **Cost and abuse**: each generation costs us real money. Price every model
  above provider cost with margin (`lib/models.ts`), max 3 open jobs per user,
  rate limit per IP on sign-up, no free credits without a verified email.
- **Moderation and law**: block prompts/images of real people's faces for
  impersonation, sexual content, minors. No face swap, no real-person
  lip-sync, no "train on a face" (out of scope in the recon). Keep the
  provider's safety checker on. Label outputs as AI-generated (EU AI Act
  transparency).
- **File size limits**: images ≤ 20 MB, jpg/png/webp, checked on the server
  from the bytes, not the extension.
- **Realtime**: polling first; Supabase Realtime on `generations` later.
- **GDPR deletion**: deleting the account cascades rows and a job removes the
  user's Storage folder; Stripe customer kept only for invoices.
- **Time zones**: all `timestamptz` in UTC, shown in the user's locale.

## 5. Build order

1. **Vertical slice** (S02, S03, S05, S06): sign in, write a prompt, pick a
   model, see the cost, Generate with the `mock` provider, watch it progress,
   see it in the gallery. Tables: all credit tables + `generations`. Routes:
   models, generations (POST/GET), webhook stub, reconcile.
2. **Must-haves**: image→video with uploads (S03), motion presets with
   preview clips (S04), video detail with download/delete/regenerate (S07),
   credits page (S10), not-enough-credits modal (S11), pricing + Stripe
   (S09), moderation, real `fal` provider behind an env key.
3. **Should-haves**: favourites and filters, cancel, upscale, image
   generation as a starting frame (S08), email when ready, landing/explore
   (S01).
4. **Fixes** from `/replica-entrepreneur` once it runs (expected: transparent
   pricing, refunds on failure shown in the ledger, no credits that vanish).

## Needed from the owner before going live

- A fal.ai API key (or another provider's) — the app runs on `mock` until then.
- Stripe account (test mode is enough to build).
